## Resolution pass — later 1 Aug 2026

This section supersedes §§2–4 and the first three bullets of §7 below. The older
detail remains because it records the reproductions and failure modes.

**Resolved and deployed in `f8ee626` on 1 Aug 2026:**

- The bar's six order mutations now require and send `eventId`; the regression was
  observed failing with every URL unscoped before the fix. An admin or host who can
  see a bar without holding its bearer token no longer gets `400 "which party?"`.
- The service worker is **push-only**. It has no fetch handler and builds no offline
  shell. Its first activation deletes legacy `cocktails-*` caches and reloads those
  legacy clients once; later deploys do not force-reload open pages. There is no
  permanent `EVACUATE` switch to remember to turn off.
- Photos pass `{ imageOrientation: 'from-image' }` to `createImageBitmap`, so EXIF
  rotation and mirrored-orientation values are applied consistently before cropping.
- Recordings request EC off, noise suppression off, auto gain on and 48 kHz, then
  ask `MediaRecorder` for 128 kbps.
- The guest menu refreshes on window `focus` as well as phone visibility and its
  one-minute poll.
- `POST /api/orders` now derives the same generated/curated menu as the public menu
  endpoint and rejects stale or invented order lines. Legitimate configurator
  variants of the six house drinks remain valid.
- `staffByIdUnscoped` accepts only a branded ID obtained from a hashed staff session;
  callers that already hold a scoped row no longer perform an unscoped lookup.

**Verified:** format check; `svelte-check` at 0 errors/0 warnings; 423 Vitest tests;
production build; 14/14 Playwright journeys. The order, menu, worker, photo,
recording and focus regressions were each seen failing for their stated reason before

## 2. Resolved in worktree — historical `EVACUATE` incident

[`src/service-worker.ts`](../src/service-worker.ts):

```js
const EVACUATE = true;
```

**While this is true, every deploy force-reloads every open page** on any device
whose worker is being replaced. That is deliberate — it is the only lever that can
drag a stuck phone forward — but it is not a resting state. On party night a deploy
will jolt a bartender's screen mid-round. (The round survives: the basket is written
to storage on every change.)

**Flip it to `false` and deploy once the stragglers are through.** One line, no other
change needed.

Two things about it that are _not_ obvious and cost real time to find:

- **Do not `await client.navigate()` inside `waitUntil`.** Activation holds the
  worker before its `fetch` handler serves anything, and navigating issues a request
  that same worker must answer — deadlock. It hung a tab so hard that even reading
  the page timed out. It is chained _after_ activation now, and not awaited.
- **Only evacuate when `replacing`.** `registration.active` during `install` is null
  exactly when nobody has been here before. Reloading a first-time visitor achieves
  nothing and broke eight e2e specs by yanking the page out from under Playwright.

Also in that commit, and worth keeping regardless of the flag: **`cache.addAll` was
replaced with per-entry `cache.add`.** `addAll` is atomic, so one timeout among 72
requests rejected the whole install — and an install that rejects never reaches
`skipWaiting()`, so the previous worker keeps the origin **indefinitely**. Every
entry answers 200 from a desk; one flaky moment on party wifi is enough. This is the
single most likely cause of the problem in §3 and it is now fixed.

## 3. Resolved in worktree — historical iOS stale-build incident

**The live symptom.** Dan's iPhone, and others, sit on a build from before any of the
worker fixes. Safari can be freed by clearing data; **Chrome on iOS shows the old
version and will not come forward.** Force-quit does nothing. A phone restart does
nothing. Only clearing browsing data works, which is why it has not been done.

### What has been ruled out, with evidence

Do not re-run these. Each was a plausible theory and each is dead:

1. **Not the Cloudflare edge.** Every HTML path returns `cf-cache-status: DYNAMIC`
   and `Cache-Control: no-cache`. Checked on `/`, `/e/<id>`, `/host/<id>`, `/admin`.
2. **Not a failed precache install.** All **72** entries in the deployed manifest
   return 200. (`addAll`'s atomicity was still a real hazard — see §2 — just not
   provably the one that fired.)
3. **Not an HTTP cache keyed by URL.** A URL the device had _never fetched_
   (`/e/<id>?v=2`) **still served the old app.** This is the decisive one: a fresh
   URL cannot hit a stale cache entry, so whatever is intercepting does so by
   **scope**, not by URL. That means a service worker.
4. **Not a different hostname.** Confirmed with Dan: it is and always has been
   `cock.meridew.com`.

### What is left, and the hard constraint

The constraint that shapes every option: **an already-stuck client cannot be sent an
instruction it has no code to understand.** An admin switch on an API response, or a
flag in the HTML, is only meaningful to a client that already has the code to read
it. These devices do not.

**The service worker is the one exception** — the _browser_ fetches, installs and
runs it without our old code participating — and `/service-worker.js` is uncacheable
at the edge (Cloudflare Cache Rule) and in the browser (`updateViaCache: 'none'`).
That is why §2 is shaped the way it is.

**Nothing reaches a device that never makes a request.** That is not solvable.

### Next steps if it is still stuck

1. Check **Settings → bottom** for the build date. That is what the stamp is for; it
   turns "which version is this" into a five-second question instead of "can you see
   a feature that only exists in the new one".
2. If the date is old, the device is not fetching the worker, and the only remaining
   lever is a **per-site** data delete — much gentler than what Dan was avoiding:
   - **Safari:** Settings → Apps → Safari → Advanced → Website Data → search
     `meridew` → swipe → Delete. Touches nothing else on the phone.
   - **Chrome iOS:** ⋯ → Delete Browsing Data → **Time range: All time**, untick
     _Browsing History_, tick _Cookies, Site Data_ + _Cached Images and Files_.
     History survives; other sites' logins do not.
3. **What a user loses** by route — this decided the design and is worth keeping:

   |                 | Caches  | Sign-in  | Bar shift | Guest identity | Round in progress | Notifications |
   | --------------- | ------- | -------- | --------- | -------------- | ----------------- | ------------- |
   | Evacuate flag   | cleared | kept     | kept      | kept           | kept              | kept          |
   | Clear site data | cleared | **lost** | **lost**  | **lost**       | **lost**          | **lost**      |

   Clearing site data costs a guest their `device_id`, so **the bar sees a stranger
   and must admit them again**, and costs a helper their `staff_token` mid-shift.

### Still proposed, still not decided

`/_app/version.json` and `/manifest.webmanifest` go out with **no `Cache-Control`**
— only `etag`/`last-modified`. That is the same defect `b16deb9` fixed for HTML, and
it means `updated.check()` (what raises the "There's a newer version" bar) can be
answered from the browser's own HTTP cache. **`hooks.server.ts` cannot fix it**:
sirv serves `/_app/*` before hooks ever see the request. Two ways:

- a **Cloudflare response-header rule** — dashboard only, no deploy, same lever as
  the existing Cache Rule for the worker; or
- the **custom-server pattern** already written up in
  [`svelte.config.js`](../svelte.config.js): import `build/handler.js`, set the
  header for those paths, delegate the rest.

And the older, larger question from 31 Jul still stands: **the worker's precaching
has caused every failure of this kind, and only push actually needs a worker.**
Stripping it to push-only would delete more code than it adds.

## 4. Resolved in worktree — historical "which party?" bug

**Reported, audit started, not finished. This is where the session was interrupted.**

Dan: _"When clicking 'ready' on an order I briefly see 'which party' and then it
disappears. I don't think the workflow is watertight in that area."_

### What the message means

`requirePartyInScope` in [`src/lib/server/scope.ts`](../src/lib/server/scope.ts)
resolves the party from **either** a bar token **or** `?eventId=`. With neither, a
caller who _has_ an account gets **400 "which party?"** (an anonymous one gets 401 —
that asymmetry is deliberate and documented there).

So the message means precisely: **a signed-in account holder, with no bar token,
called an order endpoint without naming a party.**

### The finding so far

In [`src/lib/api.ts`](../src/lib/api.ts), the read threads the party but **none of
the mutations do**:

```ts
listOrders(eventId?)   →  /orders?eventId=…      ✅ threads it
setStatus(id, …)       →  /orders/:id            ❌ token only
deleteOrder(id)        →  /orders/:id            ❌
clearOrders(which)     →  /orders/clear          ❌
bumpOrder(id, …)       →  /orders/:id/bump       ❌
admitOrderGuest(id, …) →  /orders/:id/admit      ❌
setItemProgress(id, …) →  /orders/:id/progress   ❌
```

All eleven endpoints using `requirePartyInScope` are listed by
`grep -rln requirePartyInScope src/routes/api/` — six orders, five staff.

**This is the same bug class as `701c2cb`** ("a helper could ask to serve and nobody
would ever see it"), where `GET /api/staff` 400'd for an account-holder without a bar
token and `eventId` had to be threaded through all five staff calls. The order
mutations were not audited at that time.

### The bit that was not yet established

Why a bar screen — which normally _does_ hold a token — hits this at all. The
candidate under examination when work stopped:

`Bartender.svelte` decides what to render from **the actor, not the token**:

```js
let working = $derived(can(session.actor, 'orders:advance', party(eventId)));
```

That is right in principle (an admin is entitled by who they are, not by holding a
bearer token) — but it means **the queue and its buttons render for someone with no
bar token**, and every mutation above then 400s. An admin who reaches `/bar/<id>`
without tapping "Work it" is the likely reproduction. The flash-then-vanish fits a
poll clearing the error a moment later.

### Suggested fix

Thread `eventId` through all six order mutations exactly as the staff calls were —
the server already prefers the token's own party when one exists, so it is additive
and cannot cross tenancy. Then decide whether `Bartender` should _acquire_ a token
when the actor is entitled but tokenless, rather than rendering controls that fail.

**Verify by reproducing first.** The house rule applies: a regression test has to be
seen failing.

## 7. Offered, agreed in principle, **not built**

- **Selfie mirroring — orientation half resolved in the current worktree.** Dan
  reports the photo "reverses itself" after capture.
  Diagnosis has two candidates and **the deciding test has not been run**: hold up
  writing — _backwards text = mirror, sideways head = rotation_.
  - Regardless of the answer, `createImageBitmap(file)` in
    [`src/lib/photo.ts`](../src/lib/photo.ts) passes **no options**, so EXIF handling
    is engine-dependent. `{ imageOrientation: 'from-image' }` is a one-word
    correctness fix and may be the whole thing — orientation values 2/4/5/7 encode a
    **mirror**, not just rotation.
  - If it is the OS mirroring the front camera instead, the fix is a **Flip toggle**,
    not automatic mirroring: `capture="user"` only _requests_ the front camera and
    people also pick from the gallery.
  - Worth deciding deliberately: an un-mirrored photo is what the _bartender_ sees,
    which is the whole point of the avatar. The preview may be what is lying.

- **~~Recording quality.~~ Resolved in the current worktree.** `getUserMedia({ audio: true })` in
  [`SoundRecorder.svelte`](../src/lib/components/SoundRecorder.svelte) gets the
  **voice-call pipeline** — `echoCancellation`, `noiseSuppression` and
  `autoGainControl` all default on, and on many platforms that forces **mono at
  16 kHz**. No encoder setting recovers that. Proposed: EC **off**, NS **off**, AGC
  **on** (it evens out mic distance), request 48 kHz, and set
  `audioBitsPerSecond: 128000`. Measured today: ~105 kbps Opus already, so the
  bitrate was never the problem. Size check: 5 s @ 128 kbps ≈ 107 KB base64, well
  under the 256 KB cap.

- **~~Menu refresh on window `focus`.~~ Resolved in the current worktree.** `visibilitychange` does **not** fire when
  switching between two windows side by side on a desktop — which is exactly how
  someone tests "does the menu update". Three lines next to the existing listener in
  [`src/routes/e/[id]/+page.svelte`](../src/routes/e/[id]/+page.svelte).

- **Draft persistence for work sheets** (offered as option 4 of the unsaved-changes
  fix, deliberately held). Ticks to device storage like the basket, so a killed app
  returns to your work. Adds a second source of truth; not obviously worth it now
  that the four exits are guarded.

- **~~`POST /api/orders` does not validate against the short list.~~ Resolved in the
  current worktree.** The server uses the same generated menu and short list as the
  guest response. A stale basket gets 422; legitimate configurator variants remain
  accepted.

## 8. Things proven this session, so nobody re-checks them

- **The menu genuinely updates when stock or the short list changes.** Both paths
  were driven end to end in a browser: removing Tequila dropped drinks 61 → 48 and
  removed Margarita from the featured list; the short list moved 5 → 2 → 61 → 5 on an
  open page with no reload. The 60 s poll and the `visibilitychange` refetch are both
  present in the deployed bundle (`_app/immutable/nodes/9.*`). **If it looks stale,
  it is a stale bundle on the device — see §3, not a logic bug.**
- **Sounds work end to end**: takes stored, unlabelled ones auto-named, unknown cue
  and non-audio payloads refused, a take id from one party 404s at another, clips
  decode with real durations, all enabled takes preload on arrival, disabling drops a
  take from the guest payload while the host keeps and can still play it, and mute
  silences playback without affecting ordering.
- **Work sheets no longer lose ticks**: sticky action bar pinned across a 2,306 px
  list; header reads _Done_ when clean and _Save and close_ / _Discard_ when not;
  Discard, Escape and **real Back** all confirm and all stay put when refused; Save
  and close only closes on success.

The one thing **not** provable without hardware: the microphone permission flow in
`SoundRecorder`. Encoding was exercised by feeding an oscillator through
`MediaRecorder` (real `audio/webm;codecs=opus`, real bytes), but `getUserMedia`'s
prompt needs a real phone.
